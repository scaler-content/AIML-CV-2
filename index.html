A CNN reaches 99% training accuracy. Should we trust it on new images? This post shows how to read the evidence, and which interventions help for which reason.

By the end you will be able to

  1. Explain overfitting using training and validation curves
  2. Distinguish underfitting, a good fit, and overfitting
  3. Describe Batch Normalization, Dropout, weight decay, data augmentation, learning-rate scheduling, and early stopping

01

The 99% model

Big question

A CNN achieves 99% training accuracy. Should we trust it on new images?

Training accuracy only tells us how well the model fits data it has already seen. The number we actually want is performance on held-out data. The rest of this post is about how to measure that gap, why it opens, and how to close it responsibly.

The learning journey

Observe failure
↓
Diagnose evidence
↓
Choose targeted intervention
↓
Run controlled experiment
↓
Compare validation behavior
↓
Keep the simplest solution that works

Every section below follows this loop: predict → run the experiment → inspect evidence → explain the result.

A habit worth building

For every intervention ask: What problem are we solving? What do I predict? What evidence would confirm it? Connect a technique to a mechanism instead of saying "Dropout prevents overfitting".

02

The experimental setup

We continue with CIFAR-10: RGB, 32×32 images, 10 classes. We deliberately use a small training subset. This is a teaching choice that makes the generalization problem visible without a large training run.

Important

The exact accuracy numbers are not the lesson. The learning-curve pattern is. Results can vary with hardware and random seed.

The baseline model

Four 3×3 conv layers (64 → 128 → 256 → 256 channels) with two max-pools, global average pooling, and one linear layer for 10 classes. It has 963,466 trainable parameters, which is a lot of capacity for 4,000 images.

train_tf = transforms.ToTensor()
test_tf = transforms.ToTensor()
train_full = datasets.CIFAR10("./data", train=True, download=True, transform=train_tf)
test_full = datasets.CIFAR10("./data", train=False, download=True, transform=test_tf)

train_idx = list(range(4000))
val_idx = list(range(2000))
train_ds = Subset(train_full, train_idx)
val_ds = Subset(test_full, val_idx)
train_loader = DataLoader(train_ds, batch_size=128, shuffle=True, num_workers=2)
val_loader = DataLoader(val_ds, batch_size=256, shuffle=False, num_workers=2)

class ConvNet(nn.Module):
    def __init__(self):
        super().__init__()
        self.features = nn.Sequential(
            nn.Conv2d(3,64,3,padding=1), nn.ReLU(),
            nn.Conv2d(64,128,3,padding=1), nn.ReLU(), nn.MaxPool2d(2),
            nn.Conv2d(128,256,3,padding=1), nn.ReLU(), nn.MaxPool2d(2),
            nn.Conv2d(256,256,3,padding=1), nn.ReLU(),
            nn.AdaptiveAvgPool2d(1)
        )
        self.classifier = nn.Linear(256,10)
    def forward(self,x):
        x=self.features(x)
        return self.classifier(torch.flatten(x,1))

def run_epoch(model, loader, optimizer=None):
    training = optimizer is not None
    model.train(training)
    loss_sum=correct=n=0
    for x,y in loader:
        x,y=x.to(device),y.to(device)
        if training: optimizer.zero_grad(set_to_none=True)
        logits=model(x); loss=F.cross_entropy(logits,y)
        if training:
            loss.backward(); optimizer.step()
        loss_sum += loss.item()*len(x)
        correct += (logits.argmax(1)==y).sum().item(); n += len(x)
    return loss_sum/n, correct/n

def fit(model, train_loader, val_loader, epochs=15, lr=1e-3, weight_decay=0):
    opt=optim.Adam(model.parameters(),lr=lr,weight_decay=weight_decay)
    h={"train_loss":[],"val_loss":[],"train_acc":[],"val_acc":[]}
    for e in range(1,epochs+1):
        tl,train_acc=run_epoch(model,train_loader,opt); vl,val_acc=run_epoch(model,val_loader)
        for k,v in zip(h,[tl,vl,train_acc,val_acc]): h[k].append(v)
    return h
03

What does overfitting look like?

UnderfittingTrain poor, validation poor.
Good fitTrain good, validation good.
OverfittingTrain keeps improving; validation stops improving or worsens.

If training loss keeps falling while validation loss starts rising, overfitting is the leading diagnosis: the model continues fitting training data while generalization deteriorates. A description like that is better than the bare word "overfitting": say what the relationship between the curves is.

Visualizer · The three patterns

Schematic curves (not experiment data). Switch pattern and compare the two lines.

Common misconception

"Any train/validation gap means overfitting." A small, stable gap can be normal; the direction and magnitude matter. A gap is a clue, not proof: first rule out a bad split, preprocessing mismatch, label problems, or leakage.

Do not memorise a universal numerical threshold. An acceptable gap depends on the task, noise, dataset size and evaluation design.

04

Baseline: let the CNN overfit

First run the model with no regularization. We expect training performance to improve continuously while validation performance may eventually plateau or deteriorate. The baseline matters: without it we cannot tell whether an intervention actually helped.

The generalization gap (train accuracy − validation accuracy) shows how much better the model does on seen than on unseen examples. A growing gap is a warning sign for memorization. Use the “Gap” view above to inspect it.

Reading this run

After 15 epochs the baseline reached 0.487 train and 0.461 validation accuracy; both were still rising, so the curves had not yet clearly diverged. Judge by the relationship across epochs, not by one number.

05

Batch Normalization

A common pattern is Conv → BatchNorm → ReLU. BatchNorm normalizes intermediate activations using mini-batch statistics during training and running statistics during evaluation.

Primary role

Stabilize optimization. It may also have a regularizing effect, but it is not a universal anti-overfitting switch.

Visualizer · BatchNorm in train vs. eval mode

Compare with the baseline: the BatchNorm run learns much faster on the training set (0.820 train accuracy at epoch 15) and reaches its lowest validation loss at epoch 5, but validation loss jumps around from epoch to epoch (for example 2.8081 at epoch 11). BatchNorm may make optimization smoother and can improve validation behavior; it does not guarantee that overfitting disappears.

class ConvNetBN(ConvNet):
    def __init__(self):
        super().__init__()
        self.features=nn.Sequential(
            nn.Conv2d(3,64,3,padding=1),nn.BatchNorm2d(64),nn.ReLU(),
            nn.Conv2d(64,128,3,padding=1),nn.BatchNorm2d(128),nn.ReLU(),nn.MaxPool2d(2),
            nn.Conv2d(128,256,3,padding=1),nn.BatchNorm2d(256),nn.ReLU(),nn.MaxPool2d(2),
            nn.Conv2d(256,256,3,padding=1),nn.BatchNorm2d(256),nn.ReLU(),nn.AdaptiveAvgPool2d(1))
        self.classifier=nn.Linear(256,10)
06

Dropout

Dropout randomly masks activations during training. In train mode some activations are dropped; in eval mode Dropout is disabled.

Visualizer · Dropout mask on 16 activations

The experiment uses p = 0.5 on the pooled 256-feature vector before the classifier. Here 16 units illustrate the idea.

0.5

Prediction: why might training accuracy become lower after adding Dropout? Because training is intentionally made harder. The relevant question is whether validation performance becomes better or more stable.

Common misconception

"Lower training accuracy means the model became worse." Not necessarily: Dropout deliberately makes training harder, and what we care about is generalization behavior. In this run training accuracy ended at 0.422 and validation at 0.449.

Code 
class ConvNetDropout(ConvNet):
    def __init__(self,p=.5):
        super().__init__(); self.dropout=nn.Dropout(p)
    def forward(self,x):
        x=self.features(x); return self.classifier(self.dropout(torch.flatten(x,1)))

drop_model=ConvNetDropout(.5).to(device)
hist_drop=fit(drop_model,train_loader,val_loader,epochs=15)

Weight decay / L2 regularization

objective = data loss + λ × Σ w²

This is a simplified objective. PyTorch exposes it commonly through weight_decay in the optimizer. The intuition: the optimizer is discouraged from relying on unnecessarily large parameter values, which can encourage simpler solutions that generalize better.

Visualizer · The L2 penalty

Illustrative weights (not from the experiment). Edit them or load a preset, and see what the penalty charges.

This run used weight_decay=1e-4 and ended with 0.498 train and 0.446 validation accuracy; its best validation loss came at epoch 14.

Code 
wd_model=ConvNet().to(device)
hist_wd=fit(wd_model,train_loader,val_loader,epochs=15,weight_decay=1e-4)
08

Data augmentation

Now change the training data, not the model. For CIFAR-10, reasonable examples are random horizontal flips and small random crops.

Principle

Create label-preserving variation so the model cannot depend on exact pixel arrangements or accidental details.

Visualizer · Flip and random crop

A toy 16×16 image. The CIFAR-10 recipe is flip, then pad 4 and crop 32×32; here the padding is scaled to 2 pixels. Zero padding shows as black.

Original (label: cat)
Augmented (label: still cat)
Important caveat

Augmentation is a domain assumption. A transformation that changes the label is harmful, and more augmentation is not always better: it can hurt if the transformation is unrealistic or destroys label-relevant information. What it buys you is more realistic training variation and less reliance on irrelevant exact details.

In this 15-epoch run training accuracy ended at 0.442 and validation at 0.403. Validation accuracy is below the baseline's final value, which is a reminder that a single short run does not prove or disprove a technique.

Code 
aug_tf=transforms.Compose([transforms.RandomHorizontalFlip(),transforms.RandomCrop(32,padding=4),transforms.ToTensor()])
aug_full=datasets.CIFAR10("./data",train=True,download=True,transform=aug_tf)
aug_ds=Subset(aug_full,train_idx)
aug_loader=DataLoader(aug_ds,batch_size=128,shuffle=True,num_workers=2)

aug_model=ConvNet().to(device)
hist_aug=fit(aug_model,aug_loader,val_loader,epochs=15)

Learning-rate scheduling

A scheduler changes the optimizer's step size during training: validation plateaus → reduce learning rate → smaller updates. This is primarily optimization control, not a magic regularizer. It can help the optimizer make finer updates after progress slows, and it can indirectly affect generalization.

In the recorded run (ReduceLROnPlateau, factor 0.5, patience 2) the validation loss never went three epochs in a row without improving, so the learning rate stayed at 1.00e-03 for all 15 epochs. Try other settings on the same recorded validation losses:

        sched.step(vl)
10

Early stopping

If validation loss is best at some epoch but training continues while validation worsens, the model keeps fitting training-specific details. Early stopping uses a validation metric as a training-control signal and should restore the best checkpoint. This is why it is a form of regularization: it limits how long the model can keep fitting training-specific detail after validation stops improving.

Common misconception

"Stop when training accuracy is high." The stopping signal should come from validation behavior.

With patience=3 the recorded 25-epoch run never triggered the stop, because validation loss kept reaching new lows: the best epoch was epoch 25. Explore how other patience values would behave on the same validation losses:

Visualizer · Patience what-if

Replays the stop rule on the recorded validation loss. The restored checkpoint is the best epoch seen before stopping.

Code 
def fit_early(model,epochs=25,patience=3):
    opt=optim.Adam(model.parameters(),lr=1e-3)
    best=float("inf"); best_state=None; best_epoch=0; wait=0
    for e in range(1,epochs+1):
        tl,ta=run_epoch(model,train_loader,opt); vl,va=run_epoch(model,val_loader)
        if vl<best:
            best=vl; best_epoch=e; wait=0
            best_state={k:v.detach().cpu().clone() for k,v in model.state_dict().items()}
        else: wait+=1
        if wait>=patience: break
    model.load_state_dict(best_state)
    return h,best_epoch

The lesson is the method:

  1. keep the split fixed
  2. keep evaluation fixed
  3. change one major intervention at a time
  4. compare validation behavior
  5. keep the simplest intervention that solves the observed problem
12

Better error visualization

Accuracy compresses every prediction into correct/incorrect. Instead, inspect the actual image, the true label, the predicted label and the model's confidence: a grid of validation images titled with true: … / pred: … (confidence). Pick one wrong prediction and ask:

  • Was the model confident?
  • Is the image ambiguous?
  • Could augmentation help?
  • Is this a class-confusion issue?

Aggregate metrics are not enough; error analysis should inspect actual failure patterns.

Code 
@torch.no_grad()
def collect_predictions(model,loader,n=12):
    model.eval(); xs=[]; ys=[]; ps=[]
    for x,y in loader:
        p=model(x.to(device)).softmax(1).cpu(); xs.append(x); ys.append(y); ps.append(p)
        if sum(len(a) for a in xs)>=n: break
    return torch.cat(xs)[:n],torch.cat(ys)[:n],torch.cat(ps)[:n]
13

Data leakage: the silent generalization killer

A validation score can look excellent if train and validation contain correlated or near-duplicate samples. For example: video frames → random split → near-duplicates in both sets. The model appears to generalize, but it has seen almost the same information.

Visualizer · Random split vs. keeping related frames together

Toy example: 3 videos × 4 consecutive frames. Neighbouring frames of a video are near-duplicates. Outlined frames have a near-duplicate on the other side of the split.

trainvalidationoutlined = leaked neighbour

Validation must represent genuinely unseen, deployment-relevant examples, not merely technically different rows. Keep a final test set untouched for a last estimate after model-selection decisions.

Another reason validation can mislead

Leakage, correlated samples, poor splits or distribution mismatch.

train() vs. eval(): a real debugging trap

Dropout and BatchNorm behave differently during training and inference. Forgetting model.eval() can corrupt validation measurements: Dropout can remain stochastic and BatchNorm can use training-time batch statistics, making validation noisy or misleading.

Diagnose before you fix

Interviewers test diagnostic reasoning, not whether you can list techniques. Pattern to practise: what changes → why it might help → how you verify it.

EvidenceFirst reading
High train + low validationinvestigate overfitting
Low train + low validationinvestigate underfitting / optimization / data
High train + high validationevidence of good generalization

The AI-assisted check

Suppose a teammate shares the log above and you ask an AI assistant for ranked hypotheses with one small diagnostic experiment each. Commit to your own one-sentence hypothesis first, then compare. Do not accept an answer because it sounds plausible: test it against your learning curves and run a small diagnostic.

The leading diagnosis is overfitting / excessive memorization, because training performance keeps improving while validation deteriorates. A strong engineer also checks split quality and duplicates, leakage, preprocessing mismatch, dataset size, model capacity, and label noise.

Prompt used in this exercise

"I am training a PyTorch CNN for image classification. My training accuracy increases from 0.48 to 0.99, while validation accuracy improves to 0.58 and then falls to 0.53. Give me your top 3 hypotheses ranked by likelihood. For each hypothesis, give me one small diagnostic experiment that could confirm or rule it out. Do not rewrite my model yet."
